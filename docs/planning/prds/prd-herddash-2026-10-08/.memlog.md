Reason: prior art took 3 of 5 differentiators; history and attribution survive.

- (event) Update run started on branch docs/prd-rework; inputs: docs/prd.md (draft 2026-10-05), ADR-0001, ADR-0002, docs/research/*.md
- (decision) The problem (section 1): herdr's own notification channel is transient, lossy and silent when fully detached - active-tab popups always suppressed, delivery needs a foreground client, at most 8 notifications queue, and only two transitions (blocked, background completion) notify at all - and it keeps no history; a snapshot of the author's machine showed 10 agent panes across 9 tabs and 3 workspaces with no single place to see them.
- (decision) [pre-ADR-0001] Goal (section 2): one always-current web page, as the primary surface, answering what every agent is doing right now and which ones are waiting on the operator.
- (decision) Prior art (section 3): devswha/herdr-web-ui (MIT) and alecuba16/herdr-webui (Rust/Axum, AGPL) were installed and run against a live herdr session rather than judged from READMEs, and between them neutralize 3 of herddash's original 5 claimed differentiators, leaving only persisted history and per-account attribution as a feature pair rather than a product.
- (decision) Prior art (section 3): alecuba16's AGPL license means none of its code - token auth with expiry, HTTPS with self-signed certs, service installers for both OSes - can be copied into herddash's MIT codebase.
- (decision) Non-goals for v1 (section 4): herddash is read-mostly, not a replacement for herdr's terminal UI - no creating, focusing, splitting or killing panes, and no sending prompts or keys; no authentication, v1 binds to loopback only, auth is deferred not forgotten; no cross-host aggregation, though the data model carries a host dimension from the first commit so a later phase is additive.
- (decision) Non-goals for v1 (section 4): herddash does not disable herdr's own toasts, so both channels coexist until the page earns trust; it is not an agent orchestrator, scheduler or cost tracker.
- (decision) Users (section 5): one operator running many concurrent coding agents on their own machine, on the same machine as the browser; a later phase adds the same operator on a phone over a private network.
- (decision) Data requirement (section 6): agent records come from session.snapshot and carry terminal_id, agent_status, workspace_id, tab_id, pane_id, focused and revision, plus usually agent/display_agent, terminal_title, cwd, state_change_seq, agent_session and screen_detection_skipped; terminal_title (format like a status glyph plus the current task) is the best one-line activity signal, better than agent_status alone.
- (decision) Hard requirement (section 6.1): herdr never reports which subscription owns a pane, since several launchers exec the same claude binary; herddash must resolve it itself from CLAUDE_CONFIG_DIR in the pane's foreground process environment and map it to a human name via configuration, using an existing herdr plugin on the author's machine as the reference implementation.
- (decision) Hard constraint (section 6.1): done versus idle is not a trustworthy acknowledgement signal - both mean ready for input and differ only by per-client seen state tracked independently by each terminal client; the same pane was observed reporting idle to one call and done to another minutes later.
- (decision) Requirement (section 6.1): herddash defines acknowledgement as its own concept, derived from its own event history and its own user interaction, and does not treat the done versus idle distinction as authoritative.
- (decision) Hard constraint (section 6.1): herddash must never call pane.focus or agent.focus, because unlike reads they mutate herdr's seen state and would silently clear a completion the operator has not actually looked at.
- (decision) Requirement (section 6.1): every id herddash stores is namespaced by the host it came from, from the first commit, because herdr ids are scoped to one server and documented to collide between machines.
- (decision) [pre-ADR-0001] The board (section 7.1): one row or card per agent pane, grouped by workspace and tab, sorted so the agent that has been waiting on the operator longest is first, showing the resolved subscription name, agent program, status with time in status, terminal title as the activity line, project directory and a short output excerpt, with blocked agents visually dominant.
- (decision) [pre-ADR-0001] The detail page (section 7.2): reached by clicking a row, shows the full state-transition timeline from stored history, a longer window of recent terminal output, herdr's own agent.explain reasoning, and where the pane lives with its ids.
- (decision) Architecture (section 8): a single long-lived daemon that is both a herdr socket API client and an HTTP server, backed by SQLite, with SSE out to the browser.
- (decision) Decision (section 8): use a socket client rather than a herdr plugin, because plugin hooks fire a fresh process per event and output-related events are deliberately excluded from plugin hooks entirely, so activity cannot come from plugin events at all.
- (decision) Decision (section 8): a daemon rather than an on-demand CLI call, because only a daemon holding its own subscriptions sees every transition whether or not a terminal client is attached, which is what makes herddash strictly better than the toasts.
- (decision) Protocol constraint (section 8.1): one request per connection - a connection carries one request and response then closes; only subscriptions and waits stay open, so there is a fresh dial per call plus one long-lived connection per subscription, with no pool to reuse and no multiplexing.
- (decision) Protocol constraint (section 8.1): version-gate on ping, not a protocol number, since the JSON API has no handshake or version negotiation and the protocol integer in responses belongs to a different protocol.
- (decision) Protocol constraint (section 8.1): subscribe before snapshotting, since subscriptions deliver only live events with no history replay, so snapshotting first loses the transitions in the gap silently.
- (decision) Protocol constraint (section 8.1): there is no global agent-status subscription, so herddash must fan out one status subscription per pane, tracking the pane set from the global pane.created, pane.closed and pane.agent_detected streams.
- (decision) Protocol constraint (section 8.1): a subscribe is all or nothing - one stale pane_id rejects the whole request and closes the connection, so herddash must refresh the pane list and retry rather than assume the other entries took.
- (decision) Protocol constraint (section 8.1): decode two naming conventions - lifecycle pushes use underscored event names while the three pane-scoped streams keep dotted ones.
- (decision) Protocol constraint (section 8.1): treat events_lost as a resynchronize signal - it arrives as an error then the server closes the subscription, so recovery is a new subscription, then a snapshot on a separate connection, then replace the cache, with refreshes serialized since snapshots and events share no sequence boundary.
- (decision) Protocol constraint (section 8.1): reconnect indefinitely, since herdr restarting, handing off to a new server, or not running when herddash starts are all expected, not errors.
- (decision) Protocol constraint (section 8.1): reconcile on a timer regardless - the snapshot is the source of truth and the event stream is only the low-latency invalidation signal.
- (decision) Hard constraint (section 8.2): output is read per pane on demand since no push event for output exists, but an unbounded recent read drives a recognised full-screen agent's own scroll interface and fails outright with agent_not_idle when the agent is not idle; herddash must read visible, or recent bounded by the pane's own viewport_rows, triggered by a status change, an open detail page, or the reconcile timer for blocked panes, and must never poll every pane continuously.
- (decision) Persistence (section 8.3): SQLite holds the event history that the detail page's timeline and the how-long-blocked sort both need; retention is bounded and configurable with a finite default, and captured output is subject to the same retention as the events.
- (decision) Decision (section 8.4): generate Go types from herdr api schema --json dumped from a real 0.9.3 binary rather than hand-writing them, since the research record's field lists lean partly on an older bundled schema.
- (decision) Security posture (section 9): captured agent terminal output routinely contains API tokens, credentials and private source code, which is why this section constrains the whole roadmap; the database and any logs are created with owner-only permissions matching herdr socket's own 0600, and the browser never reaches the herdr socket directly - all herdr access is server-side.
- (decision) Security (section 9): v1 binds to loopback by default with a configurable bind address so the private-network phase is a configuration change, but shipping a non-loopback bind without authentication is out of the question; retention is finite by default because an unbounded store of agent output is a liability; authentication and the private-network phase get their own decision record before any code.
- (decision) Stack (section 10): Go, for one static binary per platform with no runtime on target, trivial cross-compilation across machines and operating systems, and a concurrency model that fits many long-lived subscription connections fanning out to many browser clients; standard library HTTP with no framework needed.
- (decision) [pre-ADR-0001] Stack (section 10): server-sent events for the one-way live feed, since browsers reconnect for free over plain HTTP, with future write actions becoming ordinary POST endpoints.
- (decision) Stack (section 10): SQLite with a pure-Go driver for real history queries with no C toolchain needed, keeping cross-compilation trivial; server-rendered templates, embedded assets and hand-written JavaScript, with no npm and no build step.
- (decision) Milestone 1 as written (section 12): read the world - connect, version-gate, subscribe, fan out per-pane status subscriptions, snapshot, reconcile, survive events_lost, reconnect, and print state to stdout with no web server, since all the protocol risk is here and it comes first and alone.
- (decision) [pre-ADR-0001] Milestone 2 as written (section 12): the board - HTTP server, SSE feed, the live page, sorted by who needs the operator longest.
- (decision) [pre-ADR-0001] Milestone 4 as written (section 12): activity - bounded output excerpts on the board and the detail page.
- (decision) Milestone 5 as written (section 12): run it unattended - launchd and systemd user units, reconnect hardening, first release.
