### Diff-scope review (bmad-review: adversarial, edge-case, verification-gap)

**R1. The shipped toolchain is never tested.** All three lenses found this independently.
- `release.yml` builds the release with Go `1.27.2`.
- `ci.yml` runs vet, `go test -race` and `TestReleaseBuild` with `go-version-file: go.mod`, which
  is `go 1.26.0`.
- `release.yml` runs no `go test` at all.
- Locally only Go 1.26.5 is installed, and the local `-dev` builds (decision `d7672978140a`) use
  whatever `go` is on PATH, because `scripts/release-build.sh` neither pins nor checks the
  toolchain.

A Go 1.27 runtime or standard-library regression (for example in `os/signal`, `net/http` or the
`modernc.org/sqlite` interaction) would ship in a release that CI reported green.
*Instance:* fix now (CODE, medium). Add a CI job that sets up the spine's release Go version and
runs `go vet`, `go test ./...` and `scripts/release-build.sh`. *Prevention:* when the spine pins a
toolchain for a deliverable, CI should test with it.

**R2. Tests that skip when a tool is missing do not prove they ran in CI.**
`TestSystemdUnitVerifies` skips without `systemd-analyze`, and `TestLaunchdAgentLints` skips
without `plutil` (`deploy_test.go`). CI runs `go test -race ./...` without `-v` and with no skip
guard. By contrast, its board-tests step explicitly fails when no tests ran (`ci.yml`). A green
run therefore cannot show that `systemd-analyze verify` executed. *Instance:* fix now (CODE, low).
Story 5.7 already requires that `TestLaunchdAgentLints` does not skip on macOS. Extend the same
guard to `TestSystemdUnitVerifies` on ubuntu. *Prevention:* any test that skips on a missing tool
needs a CI-side "did not skip" check where the tool is expected.

**R3. The release script's VCS stamping is checked only in the release job.** The VG lens
confirmed by mutation: adding `-buildvcs=false` to `scripts/release-build.sh` leaves
`go test -short -run TestRelease .` green. `TestReleaseBuild` asserts GOOS, GOARCH, `CGO_ENABLED`,
`-trimpath` and the path, but not `vcs.revision` or `vcs.modified` (`release_test.go`). The
workflow's verify step checks both, but only after release-please has already published the tag,
so a regression would leave a release without binaries until someone dispatches the workflow by
hand. *Instance:* fix now (CODE, low). Assert both settings in `TestReleaseBuild`.

**R4. The guide's shell blocks have small hazards when pasted as a whole** (ADV, ECH; checked in
`docs/install.md`):
- §1: `grep … | shasum -a 256 -c -` is not chained to `install -m 755 …`, so a failed checksum
  check still installs the binary. The prose says not to install it, but the commands do.
- Backup: if `herddash config` fails, `DB=$(… | sed …)` leaves `$DB` empty, and nothing stops the
  block. It extracts correctly on this Mac today (checked).
- Backup on macOS: the wait loop greps `launchctl print … | grep 'pid ='`. Once `bootout` has
  removed the job, `print` fails, so the loop never waits on the process itself.
- Install: `bootout … 2>/dev/null` is followed straight away by `bootstrap`.

*Instance:* fix now (DOCS, low). Use `&&` between the checksum check and the install, add
`[ -n "$DB" ] || exit`, and wait with `pgrep -x herddash`. *Prevention:* see A3. Shell in a guide
is code without a test, so keep it fail-fast.

**R5. Story 4.1's in-flight-write assertion is opportunistic** (ADV; `cmd/herddash/serve_test.go:467`).
The check that the Transition pushed before SIGTERM is in `transitions` runs only
`if printedBlocked`. If the Transition is neither printed nor recorded, the test still passes, so
the "write in progress at shutdown" case is never forced. *Instance:* defer (CODE, low). Gate the
fake so a write is held open at the signal. *Prevention:* none beyond this fix.

**R6. Engine stop is an unbounded wait** (ECH; `serve.go`, `<-engineDone`). Checked. Every herdr
and procfs call in the engine derives its timeout from the run context: `engine.go:630`, `:636`,
`:1534`, `:1559`, `:1677`, `:1815` and `:2049`, with snapshot at most 30 s. Cancelling unblocks
them. The production log shows 20 starts and 19 `herddash stopped` (one instance is still
running), with zero WARN or ERROR entries. *Instance:* accept. Revisit only if a stop is ever
observed to time out.

**R7. launchd retries a persistent `exit 1` every 30 s, indefinitely** (ADV). This is known and
documented: spec 4.2 triage #10 and the guide's "launchd has no start limit" paragraph.
*Instance:* accept.

**R8. Logs are never rotated** (ADV). Neither `herddash.log` nor `herddash.stderr.log` is rotated.
On this Mac after three days, `herddash.log` is 123 KB and stderr is 0 bytes. *Instance:* defer
and watch. Record it in `deferred-work.md` (DOCS) so dogfooding notices if it grows.

**R9. Concurrency keys differ between triggers** (ADV, ECH; `release.yml`). A manual dispatch
groups by tag and an automatic run groups by head SHA, so the two could race on one release.
Manual dispatch exists only for recovery, and `release-find.sh` refuses a release that already has
assets unless `force` is set. *Instance:* accept (low).

**R10. A release created on a commit that is not the run's head is never found** (ADV;
`release-find.sh`). Known: spec 4.3 triage #4, with manual recovery documented in the guide. All
five releases so far carry their assets. *Instance:* accept.

**R11. Lower-confidence items, all accepted:**
- A second SIGTERM falls back to the default handler and counts as a crash. launchd and systemd
  send one SIGTERM and then SIGKILL.
- `TestServeShutdownAndRestart` signals the test process, which is safe while no test in the
  package calls `t.Parallel`.
- `TestServeExitCode` can orphan its child process if it fails early.
- `force=true` leaves stale assets in place.
- An outdir inside the repository taints `vcs.modified`.
- The release ldflags include `-s -w`, which spec 4.3 specifies but CLAUDE.md does not mention.
  That last one is folded into Story 5.8's CLAUDE.md pass.
